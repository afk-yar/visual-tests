# visual-tests — полигон визуальных задач

Полигон для сравнения визуальных возможностей разных LLM. Одной задаче дают
несколько моделей; их решения (самодостаточные HTML-демки) собраны в одну
витрину с переключателем моделей.

Похожий проект (референс для идей задач/подачи):
https://gpt-5-vs-opus-4-1-coding-examples.vercel.app/

## Стек
Чистый статичный HTML/CSS/JS, без WebGL/WebGL2/WebGPU, **без сборки** (нет npm/Node/бандлера в рантайме).
Node используется только как dev-time раннер тестов (`node:assert`, без npm).

## Конвенции
- Задача = папка `demos/<task>/` + объект в `manifest.js` (с общим `prompt` и
  списком `solutions`).
- Решение модели = подпапка `demos/<task>/<model-slug>/index.html` +
  запись в `solutions[]` соответствующей задачи. → В переключателе моделей
  оболочки появится ещё один сегмент; так и сравниваются разные LLM на одной
  задаче (переключаешь сегмент — меняется решение в iframe, промпт общий).
- Реестр `manifest.js` подключается как `<script>` (кладёт `window.TASKS`),
  а **не** через `fetch` — иначе сломается `file://`.
- Демки не используют ES-module-импорты и `fetch` локальных файлов
  (совместимость с `file://`).
- Тестируемая чистая логика — в dual-mode модулях: в браузере кладут API в
  глобал, в node экспортируют через `module.exports` (см. `pendulum.js`,
  `assets/shell.js`).

## Формат сдачи решения (бери отсюда, не подсматривай в чужие демки)
Чистота эксперимента: решая задачу как конкретная модель, **НЕ читай** `demos/`
других моделей/задач — формат сдачи фиксирован здесь, заглядывать в чужой код за
ним не нужно.
- Решение = самодостаточная папка `demos/<task>/<slug>/`. Обычно три файла
  `index.html` + `style.css` + `main.js`; чисто-статичную задачу (напр. SVG)
  можно уместить в один `index.html` с инлайновыми `<style>`/`<script>`.
- Без сборки/npm/CDN и любых внешних ресурсов; без ES-module `import` и без
  `fetch` локальных файлов; без подгрузки шрифтов/картинок извне (совместимость с
  `file://` и c sandbox-iframe оболочки). Только системные шрифты.
- Демка занимает весь viewport: `html,body{margin:0;height:100%;overflow:hidden}`,
  корневой `canvas`/контейнер — `position:fixed; inset:0; width:100%; height:100%`.
  Рендер по DPR (`devicePixelRatio`, обычно с потолком 2), `requestAnimationFrame`,
  dt-based анимация с клампом большого dt.
- `<html lang="ru">`, `<meta charset="utf-8">`, `<title>«Название задачи» — «Модель»</title>`.
- Опциональная обвязка в духе остальных демок: HUD (заголовок + короткая подпись)
  сверху-слева и стеклянная `panel` с кнопками/ползунками управления внизу.

## Регламент исполнения задачи (честность эксперимента)
- **Лимит доработок — одна.** Модель сдаёт решение, затем допускается ровно
  один раунд доработки по критике/эстетике — и всё. Больше не полируем, даже
  если решение можно ещё улучшить: иначе одни модели получат бесконечную
  полировку, а другие нет — и сравнение станет нечестным.
- **Доработку делает модель, а не я руками.** Единственный раунд правок вносит
  сама модель — перезапросом/раундом критики, чтобы решение осталось
  атрибутировано ей. Ручной патч ломает чистоту эксперимента: сравниваем модели,
  а не мою правку поверх их кода.
- **Перед доработкой — бэкап v1, после — выбор лучшей (обязанность оркестратора,
  не исполнителя).** До отправки модели раунда доработки оркестратор копирует её
  первую сдачу в `tmp/backups/<task>/<slug>-v1/` (`tmp/` в .gitignore, сервер 8473
  её отдаёт). После доработки сравнивает v1 и v2 скриншотами в одинаковых условиях
  и оставляет в `demos/<task>/<slug>/` лучшую — даже если это v1. Выбор версии —
  не новая доработка, лимит не тратит. В отчёте назвать, какая версия оставлена и
  почему. Исполнителю про бэкап не сообщать — это не его зона. Прецедент:
  2026-09-23 доработка испортила SVG-коня Opus 5.5, а откатиться было не к чему.
- **Починка поломки в лимит НЕ входит.** Довести решение до рабочего состояния
  (чтобы оно вообще рендерилось: убрать пустой canvas, ошибки в консоли,
  найденные обязательной визуальной самопроверкой) можно всегда — это
  минимальная планка витрины, а не доработка. Единственная доработка тратится
  только на улучшения поверх уже работающего решения.
- **Несколько задач за раз — спроси пользователя.** Если в работу заходит больше
  одной задачи, перед стартом уточни: делать веером в субагентах или
  последовательно в текущей сессии. Не выбирай молча.

## Запуск Codex-модели (GPT-5.x) — ПРЕДВАРИТЕЛЬНЫЙ регламент
> Статус: черновик. Обкатываем на одной задаче, затем корректируем по факту.
> Проверено параметрами схемы `mcp__codex__codex` и `~/.codex/config.toml`
> (2026-07-10); боевой прогон нового слага ещё НЕ делался.

- **Генерация** — через `mcp__codex__codex`. Файлы Codex пишет сам; визуал
  проверяю я (у Codex в MCP нет browser backend). Фидбэк по багам — через
  `mcp__codex__codex-reply` по `threadId`.
- **Модель — override обязателен.** Дефолт в `config.toml` сейчас
  `gpt-5.6-terra`; без `model` поедет terra. Нужную модель передавать параметром
  `model` (напр. `model: "gpt-5.6-sol"`). Слаг сверять с `config.toml`
  (`[tui.model_availability_nux]`) — но эта секция НЕполна: рабочий слаг может в
  ней отсутствовать (проверено: `gpt-5.6-luna` там нет, а модель работает).
  Наличие в секции — достаточное, но НЕ необходимое условие; финально слаг
  подтверждается по логу сессии (см. ниже).
- **Верификация слага — по логу сессии, НЕ по словам модели.** Модель свой слаг
  не знает (на «представься» отвечает «Codex на базе GPT-5»), а неверный слаг
  может тихо откатиться на дефолт terra. Надёжный способ: открыть rollout-файл
  `~/.codex/sessions/<ГГГГ>/<ММ>/<ДД>/rollout-*-<threadId>.jsonl` и найти поле
  `"model"`. ВНИМАНИЕ (проверено на Codex `0.144.0`): в `session_meta` (первая
  строка файла) поля `"model"` НЕТ — реальный слаг лежит в событиях `turn_context`
  того же файла. Проверять грепом: `rg -o '"model":"[^"]*"' <rollout>` — должен
  вернуть нужный слаг (напр. `gpt-5.6-luna`), а НЕ `gpt-5.6-terra`. Пробный вызов
  делать ДО боевого прогона; `threadId` берётся из ответа `mcp__codex__codex`.
- **Пробный вызов тоже `sandbox=workspace-write`.** Хук
  `~/.claude/hooks/codex-enforce-sandbox.js` блокирует `read-only` для
  `mcp__codex__codex`. Поэтому пробный вызов — `workspace-write` + в промпте явный
  запрет читать/писать файлы (cwd = пустая `visual-tests-tmp`).
- **Против подсматривания — физическая изоляция cwd.** `cwd` = отдельная папка
  ВНЕ репо: `E:\_Проекты\pet\visual-tests-tmp` (под writable-root `E:\_Проекты`).
  Codex пишет туда самодостаточную демку по промпту; готовый результат я
  переношу в `demos/<task>/<slug>/`. Чужих решений на пути `..` нет — не обещание
  модели, а отсутствие доступа. **После переноса `visual-tests-tmp` очищать**
  (иначе следующая модель подсмотрит предыдущую).
- **Против веб-поиска.** В сессии Codex подключён Exa MCP (`[mcp_servers.exa]`) —
  поиск по умолчанию доступен. Запрещать явно в промпте + я проверяю по tool-calls
  в ответе Codex, что Exa не дёргался. Полное снятие Exa через inline
  `config`-override НЕ проверено — не полагаться.
- **Параметры сессии:** `sandbox=workspace-write`, `approval-policy=never`.
- **Промпт** = дословный `prompt` задачи из `manifest.js` + техобвязка из секции
  «Формат сдачи решения» (самодостаточно, без сборки/CDN/`fetch`/ES-модулей;
  весь viewport; запрет читать чужие решения и искать в вебе).
- **Именование:** лейбл вида `GPT-5.6 Sol`, slug `gpt-5.6-sol`. После сдачи —
  дописать `{ model, slug, dir }` в `solutions[]` задачи в `manifest.js`.

## Как смотреть (основной режим — локальный сервер)
- **Основной режим — локальный сервер.** Двойной клик по `start.cmd` (поднимает
  `python serve.py 8473` и открывает `http://localhost:8473/index.html`),
  либо вручную: `python serve.py 8473` → `http://localhost:8473/index.html`.
- `serve.py` отдаёт `Cache-Control: no-store`, поэтому правки `manifest.js` и демок
  видны после обычного refresh — без жёсткого Ctrl+F5. (Обычный
  `python -m http.server` кэширует — тогда после правки manifest жми Ctrl+F5.)
- **Почему сервер, а не `file://`:** оболочка грузит решение в
  `<iframe sandbox="allow-scripts">` (изоляция LLM-кода). На `file://` sandbox
  даёт документу opaque-origin, и браузер блокирует загрузку `file://`-субресурсов
  (CSS/JS) внутри iframe — встроенная демка не отрисовывается. На `http://` всё
  работает. Отдельную демку (`demos/<task>/<model>/index.html`) можно открыть и
  напрямую двойным кликом через `file://` — там iframe/sandbox не участвует.
- Сервер также нужен для автономной проверки через Playwright MCP (он блокирует
  `file://`).

## Проверка визуальных результатов (правило для агента)
Любой визуальный результат проверяй **сам** через локальный сервер + Playwright MCP
(`browser_navigate` на `http://localhost:8473/...`, `browser_take_screenshot`,
`browser_console_messages`). НЕ полагайся на `file://` (Playwright его блокирует) и
НЕ перекладывай визуальную проверку на пользователя как основной способ.

## Сравнение моделей: время, токены, стоимость
- **Результат** — страница `compare.html` (пункт «Сравнение моделей» в сайдбаре,
  маршрут `#compare`), данные — `assets/compare-data.js` (`window.COMPARE_DATA`,
  без `fetch`). Считаем только исполнителей; оркестратор в стоимость моделей не входит.
- **Кто делает:** данные собирает фоновый субагент Sonnet (без `name`, с запретом
  вызывать своих субагентов) в `E:/tmp/vt-timing/all-models.json`; оркестратор
  проверяет спорные места, пересобирает `compare-data.js` и оформляет страницу,
  визуал проверяет сам (сервер + Playwright).
- **Источники:** Claude Code — `~/.claude/projects/<проект>/<сессия>.jsonl` и
  `<сессия>/subagents/agent-*.jsonl`; Codex — `~/.codex/sessions/**/rollout-*.jsonl`
  (модель — из `turn_context`). Логи Claude Code хранятся `cleanupPeriodDays`
  (с 2026-09-26 — 365 дней); более старые — только из бэкапа restic.
- **Токены Claude Code:** одна API-реплика пишется несколькими строками с одним
  `message.id`, и `usage.output_tokens` растёт от строки к строке — берём
  **последнюю** строку на `message.id`, строки `model: "<synthetic>"` отбрасываем.
  Раскладка: вход без кеша, запись в кеш (5m/1h), чтение кеша, выход.
- **Токены Codex:** `token_count` → `info.total_token_usage` накопительный, берём
  последнее значение; `input_tokens` включает `cached_input_tokens`,
  `output_tokens` включает reasoning.
- **Время первой версии** — от первой записи исполнителя до его последнего ответа
  перед первым сообщением критики ([ДОРАБОТКА]/[ПОЧИНКА]). Служебное «Output token
  limit hit» — продолжение первой версии. Доработка, починка и перезапуски
  считаются отдельно; многочасовые паузы ожидания из времени вычитаем. Вид
  субагента (решение / доработка / повтор) определяем по `description` в
  `agent-*.meta.json`, а не по дате запуска: доработка бывает отдельным
  субагентом на следующий день.
- **Стоимость** — по прейскуранту API (Claude — справочник скилла `claude-api`,
  GPT — developers.openai.com), это оценка, а не списания по подписке.

## Как тестировать
- Чистая логика: `node demos/<task>/<model>/*.test.js`, `node assets/shell.test.js`.
- UI/canvas: Playwright MCP (навигация на localhost, скриншот, проверка консоли).
